# 课程报告智能助教（Agent）设计文档

## 设计目标

本项目旨在构建一个面向教师与学生的网页端智能助教系统，核心目标是把教师在课程报告审阅中最耗时的环节（阅读长文本、发现疑点、反复追问、整理沟通结论）尽可能前移到 Agent 自动处理流程中：学生先上传报告，系统异步完成分析并抽取关键疑点，再在实时语音阶段进行高效率追问，最终自动生成融合“报告原文事实 + 学生解释信息”的总结报告，并支持学生在阅读后提交补充意见以持续修订版本。系统的定位是“辅助理解与沟通整理”，不直接替代教师最终评分裁量；同时通过沉淀课程要求与案例问法，将提问能力固化为系统内能力，减少每次重复配置的成本。

## 工作流程

### 1）学生上传报告
学生进入网页后先选择课程与作业项，再上传课程报告文件（PDF/Word/Markdown 等），系统会立即创建一次会话记录并保存原始文档和基础元信息（学生标识、课程标识、上传时间、作业题目），随后进入后台分析队列。

### 2）系统异步分析报告
系统在后台执行文档解析与语义分析，不要求实时返回，重点是稳定和准确：先将报告拆分为章节级内容，再与课程要求和系统内置案例模式对齐，产出“关键点清单、待澄清问题、优先级、证据段落引用”。分析完成后，前端提示“分析已完成，可进入问答阶段”。

### 3）学生进入实时语音问答
学生进入语音问答页面后，系统加载上一阶段产出的问题计划并启动实时语音会话；Agent 按优先级发问，学生语音回答后，系统实时判断答案是否充分。若信息不完整则继续追问或换角度提问，若回答已覆盖关键点则推进到下一问题，必要时可基于当前回答动态生成新问题，直到系统判断信息覆盖度达到阈值为止。

### 4）系统生成总结报告
问答结束后系统自动生成总结报告，内容同时包含：报告原文中的核心结论、学生在追问中的补充解释、仍需教师重点关注的风险或不确定点。该总结报告是可读版本，便于学生与教师快速把握作业沟通结果。

### 5）学生提交修改意见并迭代
学生阅读总结后可提交“补充事实、措辞修正、结构调整”等意见，系统基于原报告、问答记录和修改意见进行受控更新，形成新版本总结，并保留版本历史用于后续追溯。

## 实现技术方案

### 前端技术栈（Web）
前端建议使用 `React + TypeScript + Next.js` 构建，`Ant Design` 或 `shadcn/ui` 作为组件层，`TanStack Query` 处理异步任务状态，`WebSocket` 或 `SSE` 用于后台分析完成通知，语音页面通过 `WebRTC + MediaRecorder + Web Audio API` 采集麦克风音频并展示实时字幕、提问状态、网络质量与重连提示。上传模块支持分片上传与断点续传（如 `tus` 或对象存储 SDK），避免大文件失败重传。

### 后端技术栈（服务层）
后端建议采用 `Python FastAPI`（也可选 `Node.js NestJS`，但基于你后续模型编排和数据处理场景更推荐 Python 生态），以 REST API 负责鉴权、文件会话管理、任务创建、报告版本管理；以 `Celery/RQ + Redis` 承载异步分析与总结任务；以 `PostgreSQL` 存储业务数据（用户、课程、会话、问题、问答转写、总结版本）；以对象存储（如火山引擎 TOS 或兼容 S3）保存报告原件和输出文档；并增加统一审计日志，便于定位模型决策来源。

### 文档分析与问题生成 API
文档分析流程分为“解析、检索、推理”三段：解析层可用 `unstructured`、`python-docx`、`pdfplumber` 等提取可检索文本；检索层用向量检索（`pgvector` 或 Milvus）将课程要求、案例模板、历史高质量问答进行召回；推理层调用文本大模型 API 生成结构化输出（关键点、疑点、证据片段、追问草案）。建议把大模型输出约束为 JSON Schema，避免自由文本导致前端难以消费。

### 实时语音交互 API
实时语音阶段建议采用“豆包语音模型主对话 + 业务策略护栏”的混合架构：豆包语音模型负责语音输入到语音输出的一体化理解与推理，业务后端负责注入课程约束与会话状态，保证问答不偏题。接入上按火山引擎官方文档使用 [豆包语音交互大模型 API](https://www.volcengine.com/docs/6561/1594356?lang=zh#python%E7%A4%BA%E4%BE%8B)，由实时网关统一处理会话建立、音频流收发、断线重连、超时控制和会话结束。实时轮次中不直接把整份报告塞入上下文，而是使用“每轮小上下文注入”：先将异步阶段产出的提问策略（必问点、追问条件、结束条件、禁问边界）作为会话级 system 指令，再用“当前问题 + 学生本轮回答转写 + TopK 报告证据片段（3~5段）+ 历史结构化摘要”作为本轮上下文输入，这样既能让模型知道报告细节，又能控制延迟。为避免上下文膨胀，历史对话不全量回放，只保留结构化状态（已覆盖点、未覆盖点、冲突点、证据 chunk_id、下一步动作），并在每轮结束后增量更新。若学生表述与报告证据冲突，模型优先执行澄清追问；连续冲突时打标记进入教师复核。性能上建议将重任务前移到异步阶段，实时阶段仅保留 ASR/语音推理、轻量检索和短文本决策，并通过并行化（边转写边检索）、检索缓存、输出长度控制来保障首句响应速度。

### 报告生成与修订 API
总结报告生成建议复用文本大模型 API，但使用独立 Prompt 模板与更严格的结构约束，确保输出固定章节（报告摘要、关键解释、未澄清点、教师关注项）。修订阶段调用同一模型的“受控改写”接口逻辑：输入旧版本总结 + 学生补充意见 + 原始问答证据，输出新版本并附变更说明，避免模型在修订时引入无来源内容。

### Agent 编排与结束策略
系统内部需建立一个轻量决策器来控制提问终止条件，建议综合“关键问题覆盖率、每题答案完整度评分、追问轮次上限、会话时长上限、学生主动结束意图”多维信号。实现上可采用“规则引擎 + 小模型评分 + 豆包语音模型复核”的组合：策略层负责给出 Continue、Clarify、Next、Done 四类动作，豆包语音模型负责将动作转成自然语音问法，既保证教学可控性，也保持对话自然度，并在日志中记录每次决策依据以便复盘。

### 安全、权限与可运维性
系统需实施分角色权限（学生仅可访问本人会话，教师/管理员可访问课程范围数据），敏感数据（报告正文、语音转写）默认加密存储，API 侧采用 JWT/OAuth2 与请求级审计。运维上需提供任务重试、死信队列、模型调用失败降级策略（例如语音失败后转文本问答），并对关键指标做监控：分析成功率、平均分析时长、语音平均延迟、问答完成率、总结修订率。

## 需要数据支持

### 课程标准与评分要求数据
需要课程级的标准化输入，包括课程目标、作业题目、评分维度、必答要点和教师关注风险点，这些数据用于驱动系统在分析与提问阶段的“对齐判断”，决定该问什么以及问到什么程度才算完整。

### 案例与问题模板数据
需要一批可复用的历史案例（可脱敏）和对应的高质量追问方式，最好带上标签（课程类型、常见薄弱点、提问风格、参考答案特征），用于构建系统的固有提问能力，使 Agent 能在新报告场景下自动检索并复用有效问法。

### 学生报告样本数据
需要覆盖不同质量层级的真实报告样本（优秀、中等、薄弱），用于校准文档分析准确性和追问难度，避免系统长期偏向某一类文风或表达能力，影响提问公平性与总结质量。

### 语音交互质量数据
需要采集语音链路相关数据，如音频采样参数、网络质量、ASR 错误类型、平均端到端延迟、打断率等，用于优化实时交互体验和接口参数配置，确保语音阶段具备足够实时性与稳定性。

### 运行反馈与人工标注数据
需要在系统上线后持续积累会话日志、学生修订意见、教师反馈与人工评审标注，这些数据用于迭代“是否答全”的判断标准、总结报告质量评估标准和提问策略，形成可持续优化闭环。

## 风险与依赖

该项目的主要风险在于复杂报告解析误差可能导致提问偏离重点、实时语音链路在弱网环境下产生体验波动、以及多模型串联带来的成本与稳定性压力，因此需要在架构上提前设计降级方案和监控体系；外部依赖主要包括语音与文本模型 API 可用性、对象存储与消息队列稳定性、以及校内数据合规策略，这些依赖应在项目初期通过 PoC 验证并形成明确的 SLA 与应急预案。
